# RestoMind — архитектура и соглашения

Документ описывает **текущее состояние** репозитория и правила разработки. Исторический каталог `rest_ai_agent/` не используется — код живёт в `app/` (см. [README.md](README.md)). Дерево каталогов и ориентация по модулям — [codebase.md](codebase.md).

---

## Назначение

Интеллектуальный оператор для ресторана: общение в **WhatsApp**, понимание естественной речи (**OpenAI**, structured JSON → Pydantic), заказы с подтверждением, бронирование столов, FAQ, эскалация на оператора. Интеграция с **iiko Cloud** (меню, стоп-листы, отправка доставки). Админ-панель: дашборд, канбан, live-чаты (WebSocket + Redis Pub/Sub), аналитика.

## Правила разработки

1. **Async-first** — I/O (БД, Redis, внешние API) через `async`/`await`.
2. **Вебхук WhatsApp** — быстрый ответ `200 OK`; тяжёлая логика в `BackgroundTasks`.
3. **Структурированные ответы ИИ** — парсинг в Pydantic (`AIBrainResponse`), без ручного разбора JSON регулярками.
4. **Тонкие роутеры** — в `app/api/` только приём запроса и вызов сервисов; ветвление — в `app/services/`.
5. **Цены и номенклатура** — из БД / контекста меню (`build_menu_context` в `order_logic.py`); модель не придумывает цены.
6. **UUID iiko** — в заказах использовать привязку к `MenuItem.iiko_id` там, где это реализовано в `intent_router` / `order_logic` (см. код).
7. **Консистентность данных (versioning):** обновление активного черновика заказа из чата — через **optimistic locking**: колонка `orders.version` (ORM `Order.row_version`), `UPDATE … WHERE id = ? AND version = ?`, при конфликте — понятный ответ клиенту «напишите ещё раз».
8. **Идемпотентность входящих сообщений:** вебхук Meta может дублировать доставку — **Redis** (`wa:dedupe:{message_id}`) + таблица **`whatsapp_inbound_dedupe`** (первичный ключ `message_id`) с `ON CONFLICT DO NOTHING`; резервация в отдельной короткой транзакции до основной обработки.
9. **Redis ≠ источник истины:** заказ и состав — в **PostgreSQL** (`orders.items_json`); Redis — сессия чата и кэш. При потере Redis: **резерв состояния** в `users` — `current_state`, `current_pending_order_id`, `current_pending_booking_id` (синхронизация из `dialog_mgr` при смене Redis-state; при miss в Redis — восстановление из БД). Дополнительно: **`chat_logs`** и последний **DRAFT** заказа; полная автоматика без пробелов — см. roadmap v3.

## Реализованный функционал (сводка)

- Диалоги с историей в Redis, состояния: `CHATTING`, `AWAITING_ORDER_PAYMENT` (выбор оплаты перед Да/Нет), `CONFIRMING_ORDER`, `CONFIRMING_BOOKING`, `HUMAN_MODE`.
- Контекст меню для OpenAI: текстовый каталог с ценами и `[id: …]` (не векторный RAG).
- Подтверждение заказа и брони словами да/нет; отправка заказа в iiko **только после действия оператора** в админке (переход `confirmed` → `sent_to_iiko`, `create_delivery_order`).
- Перехват оператором, пауза ИИ (`ai_paused`), сообщения оператора в WhatsApp; WebSocket-события для админки.
- Стоп-листы iiko, фоновое обновление; поле `iiko_last_error` у заказов при ошибках.
- Админка: авторизация по cookie, аналитика, интеграции, демо-данные, редактирование меню (см. [CHANGELOG.md](CHANGELOG.md)).
- **Резерв диалогового state в БД:** поля `User.current_state`, `current_pending_order_id`, `current_pending_booking_id` — дублирование Redis-сессии для восстановления после eviction/сбоя.
- **Правила упаковки в БД:** модель `PackagingRule`, расчёт в `compute_fee_lines` / `match_packaging_rule`, CRUD `GET/POST/PATCH/DELETE /api/admin/packaging-rules`, вкладка «Упаковка» в админке (без деплоя для смены цен и ключевых слов).
- **Надёжность обработки:** обёртка `process_with_retry` для вебхука (текст и голос); таблица `failed_tasks` при исчерпании попыток.
- **Аудит предоплаты:** таблица `payment_events` — запись при смене `prepayment_status` через `PATCH /api/admin/orders/{id}/payment` (вебхуки банка — следующий шаг).
- **Смешанная оплата и админка:** повторная проверка split при `PATCH` заказа; предупреждение в списке; при переходе `draft` → `confirmed` при расхождении с итогом — отказ (HTTP 409) и сброс в ожидание предоплаты.

Подробные изменения по версиям — в [CHANGELOG.md](CHANGELOG.md).

## Клиентский опыт «вау» (хостес / официант, не автоответчик)

**Цель:** уйти от образа «бота» к образу **идеального хостеса**: узнаёт постоянного гостя, понимает с полуслова, предлагает сочетания блюд с обоснованием, не ломается при правках «на ходу», даёт приятное финальное резюме заказа. Технически это сочетание **данных из БД**, **сильного промпта** и **детерминированного расчёта** на бэкенде (цены и состав — не из «головы» модели).

### Пять направлений (дорожная карта)

| # | Направление | Суть | Связь с кодом / фазами | Статус |
|---|----------------|------|-------------------------|--------|
| 1 | **Гипер-персонализация** | Имя/телефон, `operator_note`, последние заказы → тон «с возвращением!», предложение «как обычно» | `customer_context` (`app/services/customer_context.py`) + блок в системном промпте | ✅ |
| 2 | **Гастро-экспертиза (upsell с душой)** | Советы по сочетаниям; приоритет тегам из меню | `MenuItem.tags` в `build_menu_context`, `prompts.py` (RECOMMENDATION + теги), §4.2 | ✅ данные + промпт + §4.8 трасса/дашборд |

## План к реализации: RestoMind v2.0 (Логистический POS-ассистент)

Этот этап превращает бота в профессиональную систему приема заказов с учетом специфики упаковки, логистики и безопасности платежей.

**Состояние в коде (на 2026-04):** всё из снимка 2026-03 **плюс:** правила упаковки из таблицы `packaging_rules` (с fallback на legacy `.env` при пустой таблице), резерв state пользователя в `users`, журнал `payment_events`, retry + `failed_tasks`, контроль mixed split при правках заказа оператором, **статусы доставки исходящих WhatsApp** в `chat_logs` + обработка вебхука Meta `statuses`, **платёжный webhook** с колонками `orders.payment_provider` / `orders.external_payment_id` и уведомлением клиента в WA после `paid`, **опциональная очередь ARQ** (Redis) для вебхука WA и уведомления об оплате с fallback на `BackgroundTasks`, **онбординг iiko в админке** (`verify` → выбор org → `setup` + шифрование ключа). Отдельный статус `AWAITING_PREPAYMENT` в Redis **не используется** — ожидание выражено через `CHATTING` + `prepayment_status` и метаданные заказа.

### Деньги: валидация расчётов и подтверждение оплаты

Система работает с деньгами — в плане зафиксированы **конкретные механизмы**, а не только «ИИ сказал».

#### Валидатор смешанной оплаты (реализовано)

- **Правило:** `payment_split.cash + payment_split.card + payment_split.remote` должна **совпасть** с итоговой суммой заказа после расчёта бэкенда (блюда + упаковка + доставка), с допуском **±1 ₸** (округление).
- **Реализация:** `validate_mixed_payment_total()` в `app/services/order_logic.py`; вызывается из `intent_router` **до** записи заказа в БД.
- **Поведение при ошибке:** черновик **не создаётся**; клиент получает ответ с текстом ошибки — до исправления split нет перехода к шагу «Да / Нет», т.е. **к статусу `confirmed` эта ветка не дойдёт** (сначала должен появиться корректный `DRAFT`).
- **Риск «дыр в кассе» (частично закрыт):** при `PATCH` заказа в админке выполняется **повторная проверка** mixed split против пересчитанного итога; в списке заказов показывается предупреждение; переход **draft → confirmed** при расхождении блокируется. **Позиции** в модалке правятся через **«Изменить состав»** → `rebuild-draft` (пересчёт fee_lines). Тонкая ручная подгонка split без пересборки — при необходимости отдельно.

#### Подтверждение оплаты (текущий и целевой контур)

| Этап | Сейчас | Целевое развитие |
|------|--------|------------------|
| Фиксация намерения | `payment_details`, `total_price`, `prepayment_status` в `Order` | То же |
| «Деньги на счёте заведения» | Оператор вручную: `PATCH /api/admin/orders/{id}/payment` (`prepayment_status`: `paid` / `waived`, при необходимости `payment_link_url`) | Webhook от эквайринга / Kaspi / агрегатора → тот же переход статуса, **идемпотентность** по `payment_id` |
| Блокировка клиентского «Да» | WhatsApp: если `requires_order_prepayment` и статус не `paid`/`waived` — отказ | То же + (опционально) уведомление клиенту при смене статуса |
| Аудит | Таблица **`payment_events`** при смене предоплаты через админку (`event_type`, `actor`, сумма, заметка) | Webhook: идемпотентность по `note` = `provider:payment_id`; на заказе — **`payment_provider`**, **`external_payment_id`**. **Дальше:** хранить **raw payload** события и верификацию подписи провайдера (не только Bearer на `/api/webhooks/payment`) |

#### Конфигуратор упаковки (Mapping) — реализовано

- **Было:** эвристики `classify_packaging_kind` + цены только в `.env`.
- **Сейчас:** таблица **`packaging_rules`** (`kind`, `name`, `price`, `iiko_product_id`, `keywords`, `option_key`, приоритет `sort_order`); сиды при пустой таблице; расчёт через `match_packaging_rule` / `compute_fee_lines` с учётом правил; **GET/POST/PATCH/DELETE** `/api/admin/packaging-rules`; вкладка **«Упаковка»** в админке.
- **Legacy:** при отсутствии подходящего правила в БД сохраняется прежняя логика из env/классификатора.

#### Переключение контекста: голос ↔ текст

- **Факт:** состояние черновика заказа — в таблице **`orders`** (`DRAFT`, `items_json`, `total_price`); диалоговая «сессия» — **Redis** (`user:state`, `chat:history`, `pending_order` по тем же ключам `phone`).
- **Смысл:** клиент может **начать голосом** и **продолжить текстом** (или наоборот): после транскрипции голоса дальнейший `process_message` использует ту же историю и тот же `pending_order`, пока не сброшен таймут или заказ не отменён.
- **Ограничение:** при звонке PSTN (Twilio) позже понадобится явное сопоставление **номер телефона ↔ тот же user/chat key**, что и в WhatsApp.

### 1. Углубленная логика тарификации (Backend)

#### 1.1. Специфические контейнеры (Ланч-боксы)

Система автоматически рассчитывает стоимость упаковки на основе состава заказа:

| Правило | Начисление |
|--------|------------|
| **Манты** | +200 ₸ за каждую порцию (по названию/категории меню, см. `classify_packaging_kind`). |
| **Плов 0.5кг** | +300 ₸ за каждую порцию. |
| **Плов 1кг (триггер выбора)** | ИИ обязан уточнить тип упаковки: **табак** +800 ₸ или **фольгированный казан** +650 ₸ (`packaging_plov_1kg`: `tabak` \| `foil_kazan`). |

- **Логика ИИ:** запрещено переходить к расчёту итоговой суммы и созданию черновика заказа, если в позиции распознан плов 1кг, но не выбран тип контейнера (валидация в `intent_router`).

Цены и UUID номенклатуры iiko для строк заказа — в `.env` (`PACKAGING_*`, `IIKO_PRODUCT_ID_PACKAGING_*`), см. `.env.example`.

#### 1.2. Стоимость доставки (Динамическая)

- Сумма **блюд** < **10 000 ₸**: позиция «Доставка» — **700 ₸** (настраивается).
- Сумма блюд ≥ **10 000 ₸**: доставка **0 ₸**.

#### 1.3. Порог безопасности (Лимит на предоплату)

- Если **итог заказа ≥ `ORDER_PREPAYMENT_THRESHOLD_KZT`** (по умолчанию **15 000 ₸**):
  - бот не переводит клиента в шаг «Да / Нет», пока не отмечена предоплата оператором;
  - в `order_meta`: `requires_order_prepayment: true`, в БД заказа: `prepayment_status = pending` (наряду с бронями, где предоплата уже была в продукте);
  - текст в чате: необходимость предоплаты; уточнение «минимум 5000 ₸» при необходимо́м согласовании с продуктом/юридическим текстом;
  - в админке: жёлтый контур карточки и бейдж **ПРЕДОПЛАТА** при `pending`.
- Подтверждение клиентом «Да» в WhatsApp **отклоняется**, пока `prepayment_status` не `paid` или `waived` (`PATCH /api/admin/orders/{id}/payment`).

### 2. Сценарий диалога и оплата (AI Brain)

#### 2.1. Смешанная оплата (Mixed Payment)

ИИ должен уметь распознавать и структурировать разделение суммы (форматы вроде *«5к на каспи, остальное наличными»*).

**В коде (факт):** в ответе модели — `payment_mode: "mixed"` и блок `PaymentSplit` (`cash`, `card`, `remote`). В `items_json.order_meta` сохраняется:

```json
"payment_details": {
  "type": "mixed",
  "split": { "cash": 4700, "card": 0, "remote": 5000 }
}
```

Для одиночного способа: `payment_mode: "single"` и `payment_details: { "type": "single", "method": "cash" | "card" | "remote" }`.

**Инвариант:** пока математика смешанной оплаты **не сходится** с итогом, система **не создаёт** заказ в БД и **не** переводит диалог к подтверждению «Да / Нет» для этой попытки — т.е. **нельзя «подтвердить» (`confirmed`) оплату, которая не бьётся с чеком**. Отдельно: для заказов с предоплатой по порогу суммы «Да» в WhatsApp блокируется, пока оператор не отметит оплату (`paid` / `waived`).

Проверка: `validate_mixed_payment_total` в `order_logic.py` (вызов из `intent_router.py`).

#### 2.2. Мультиязычность (RU, KK, UZ, EN)

- **OpenAI:** автоопределение языка; поле `detected_language` в `AIBrainResponse`.
- **Edge-TTS:** голос по `detected_language` при `WHATSAPP_VOICE_REPLIES=true`.
- **Эвристика оплаты:** расширенные ключевые слова в `detect_payment_method_from_text` (`app/services/order_logic.py`).

### 3. Интеграция и контроль (Admin & iiko)

#### 3.1. Режим «Draft First» (контроль оператора)

- Все заказы из чата попадают в админку как **`DRAFT`**.
- Переход **`confirmed` → `sent_to_iiko`** инициирует `deliveries/create` в iiko (не из шага подтверждения клиента в WhatsApp в один клик без оператора).
- В комментарий к заказу в iiko попадают тип получения, сводка по оплате (в т.ч. mixed), номер заказа RestoMind.

#### 3.2. Визуализация в админке

- Карточка канбана: тип заказа, способ оплаты (в т.ч. бейдж **MIX**), бейдж **ПРЕДОПЛАТА**, краткое имя строки упаковки плова 1кг из `fee_lines`.
- Ошибки iiko: выделение карточки при `iiko_last_error` (как ранее).
- **Запланировано (активный продавец):** блок **«Рекомендации бота»** — что предложено, принял ли клиент (см. §4.8), чтобы видеть ценность ИИ в деньгах.

#### 3.3. Онбординг iiko через Cloud API (SaaS-уровень)

**Принцип:** автоподключение делается **только** через официальный **iiko Cloud API** (`apiLogin` → токен), как уже реализовано в `app/integrations/iiko_client.py` (`POST /api/1/access_token`, `organizations`, номенклатура). **Не** использовать логин/пароль от веб-интерфейса iiko: это не API, возможны 2FA/captcha, риск блокировки и небезопасное хранение пароля — «хак», а не продукт.

**UX (Stripe-like onboarding):**

| Шаг | Действие пользователя | Действие бэкенда |
|-----|----------------------|------------------|
| 1 | «Подключите iiko» → вставить **API-ключ (apiLogin)** → «Подключить» | Проверка ключа: получить токен, список организаций |
| 2 | (опционально) выбор организации, если у ключа их несколько | Сохранить `organization_id` (iiko) в настройках заведения RestoMind |
| 3 | Автосинхронизация | `GET organizations` при необходимости → `get_nomenclature` → существующий пайплайн **`sync_menu_from_iiko` / `menu_sync.sync_iiko_menu_to_db`** → заполнение `menu_items` (`iiko_id`, категория, цена); теги у существующих позиций **не затирать** (уже в коде) |
| Финиш | Экран успеха | «Импортировано N блюд, M категорий» + CTA «К заказам»; индикатор последней синхронизации (как сейчас для стоп-листов) |

**Псевдо-обёртка для «хочу логин/пароль»:** в UI только объяснение «получите apiLogin в личном кабинете iiko / по инструкции партнёра» — **не** выполнять вход в веб от имени клиента.

**Обновление меню:** периодический job (каждые X минут) и/или кнопка **«Обновить меню»** (тот же sync, что `POST /api/admin/integrations/sync` сегодня, но с ключом из БД организации, а не только из `.env`).

**Реализация в коде:** `app/services/iiko_onboarding.py` (`verify_iiko_api_login`, `setup_organization_iiko`); API `POST /api/admin/integrations/iiko/verify` и `POST /api/admin/integrations/iiko/setup`; UI на вкладке «Интеграции» (поле apiLogin → «Проверить ключ» → выбор организации → «Сохранить и импортировать меню», опционально terminal group). Парсер номенклатуры — тот же пайплайн, что и при `sync_menu_from_iiko`.

#### 3.4. Хранение учётных данных и кэш токена

**Сейчас:** `IIKO_API_LOGIN`, `IIKO_ORGANIZATION_ID` в **`.env`** / `settings` — fallback для dev и legacy single-tenant; у **`organizations`** — **`iiko_organization_id`**, открытый **`iiko_api_login`** (legacy) и/или **`iiko_api_login_enc`** при заданном **`APP_SECRETS_FERNET_KEY`** (сохранение из мастера админки).

**Цель SaaS / franchise:** хранить **apiLogin только в зашифрованном виде**; UUID организации и прочие идентификаторы iiko — открыто (это не секреты).

**Шифрование (рекомендация):** в `.env` один мастер-секрет **`IIKO_SECRETS_FERNET_KEY`** (или общий `APP_SECRETS_KEY`) — URL-safe base64 для **Fernet** (`cryptography.fernet`). При сохранении из админки: `ciphertext = Fernet(key).encrypt(raw_api_login.encode())`, в БД — строка (bytes → base64 text). Перед `IikoClient`: расшифровка в памяти, ключ **никогда** не логировать. Ротация ключа: поддержать `KEY_ID` / два ключа decrypt-only (вне объёма MVP).

**Кэш токена iiko:** **Redis** `iiko:access_token:{restomind_org_id}` с TTL ~10–12 мин (токен iiko ≈15 мин) — не хранить токен в БД как источник истины.

**Вопросы перед реализацией:** один `apiLogin` на филиал всегда достаточен? Нужна ли ротация ключей без простоя? Требования к аудиту (кто нажал «Подключить»)? Нужен ли **отдельный** 1:1 **`organization_integration_settings`**, если таблица `organizations` разрастётся (OpenAI per org, и т.д.)?

#### 3.5. «Магия» после первого импорта (следующие фазы, не блокер онбординга)

После успешного импорта меню можно автоматизировать качество Sales OS:

1. **Авто-теги** для AI (`MenuItem.tags`): эвристики по категории/названию («напиток», «горячее», «жирное») и/или однократный прогон лёгкой модели с жёстким allow-list тегов.
2. **Связи upsell** (позже — таблица или конфиг): пары «основное → гарнир/напиток»; не заменяет §4.12, а питает `pick_recommendation`.
3. **Черновики правил упаковки** по ключевым словам в названии (у вас уже есть `packaging_rules.keywords` — можно предложить пресеты при пустой таблице).

Всё это — **опциональные шаги мастера** с явным согласием оператора (не молча перезаписывать ручные теги).

#### 3.6. Auto Setup Score и чеклист (как у Stripe)

На Overview (или отдельный виджет): **оценка готовности** (0–100%) и чеклист: iiko подключён, меню импортировано, WhatsApp, база знаний, упаковка настроена, upsell/теги. Связь с приоритетами в [prompt.md](prompt.md) (P0–P2): даёт ощущение прогресса и снижает бросание продукта на полпути.

**Пример весов (настраиваемо):** iiko + выбранная org (25%) · меню импортировано N>0 (25%) · ≥3 правила upsell или включён дефолтный стратегия (25%) · тестовый диалог пройден / WhatsApp верифицирован (25%). Для **одной кофейни** достаточно упростить до 2–3 шагов — те же компоненты, меньше визуального шума.

**Фронт:** прогресс в шапке админки + **`GET /api/admin/setup-status`** (агрегирует флаги); доработки весов/копирайта — по продукту.

#### 3.7. Franchise-ready: tenant (сеть) и филиалы

**Зачем:** отделить **плательщика / бренд** (франшиза) от **точки продаж** (филиал с своим меню, своим iiko, своим WhatsApp).

| Сущность | Назначение | Примечание |
|----------|------------|------------|
| **`tenants`** (aka accounts) | Сеть: «Додо», холдинг | `id` (PK как в остальной БД можно оставить **Integer** для простоты FK; **UUID** — опционально для публичных ссылок), `name`, `plan`, биллинг позже |
| **`organizations`** (филиал) | Текущая таблица | **`tenant_id`** → FK `tenants.id` (nullable для legacy). iiko: **`iiko_api_login` / `iiko_api_login_enc`**, **`iiko_organization_id`**, **`iiko_terminal_group_id`** |
| **Пользователи админки** | `staff_users` | Уже привязаны к `organization_id`; при росте сети — опционально роль «владелец сети» с доступом ко всем org одного `tenant_id` (отдельная фаза) |

**Простой кафе:** один `tenant`, одна `organization`, тот же UX без лишних экранов. **Сеть:** один `tenant`, много `organizations`, у каждой свой зашифрованный ключ (или общий apiLogin на сеть — продуктовое решение: один ключ iiko часто даёт список org, филиалы выбираются при онбординге).

**Onboarding (реализовано; уточнение к §3.3):**

1. `POST /api/admin/integrations/iiko/verify` — ключ **не** сохраняется; ответ `{ organizations: [{ id, name }] }`.
2. Выбор филиала в UI админки (вкладка «Интеграции»).
3. `POST /api/admin/integrations/iiko/setup` — сохранение ключа (Fernet при `APP_SECRETS_FERNET_KEY`), импорт меню в том же запросе, опционально `terminal_group_id`.

Повторный импорт: `POST /api/admin/integrations/sync` и скрипты — без повторного ввода ключа.

**Сервис:** `app/services/iiko_onboarding.py` — `verify_iiko_api_login`, `setup_organization_iiko`; парсер номенклатуры не дублируется (`menu_sync`).

### 4. Интеллектуальная корзина и активный продавец (v2.0+)

Цель: бот не только «принимает» заказ, а **гибко ведёт корзину** и **умно допродаёт** с аргументацией (вкус, сочетание, традиция, популярность).

#### 4.1. Гибкое редактирование заказа (Chat CRUD) — как это работает

1. ✅ **Context-aware order:** при интенте `order` модель возвращает полный список `items` и/или **`order_actions`**: `add`, `remove`, `set_quantity` (схема `OrderAction` в `ai_schemas.py`). Отдельного `replace` в схеме нет — смена позиции через `remove` + `add` / `set_quantity`.
2. ✅ **State sync:** бэкенд читает **`DRAFT`**, применяет **`merge_cart_actions`**, пересчитывает тарификацию, сохраняет заказ; в промпт подмешивается **«Текущий черновик заказа»** (`format_draft_order_context_for_prompt`).

Связь с §«Переключение контекста»: источник правды по составу — **`orders.items_json`**, а не только последний ответ модели.

#### 4.2. Система рекомендаций (Upselling Engine)

1. ✅ **Сочетаемость:** в `build_menu_context` у каждой строки меню при непустом поле выводится **`— теги: …`** (`MenuItem.tags` в БД, админка: поле в модалке позиции). Синхронизация iiko **не затирает** теги у существующих позиций.
2. ✅ **Аргументация в промпте:** блоки **RECOMMENDATION_ENGINE**, **«Теги в меню (§4.2)»**, тактика upsell и few-shot примеры в `prompts.py` — гастро-логика и приоритет тегов для конкретных пар блюд.

#### 4.3. Технические изменения Backend (схемы) — ✅

Контракт **уже в коде**: `app/schemas/ai_schemas.py` — `OrderAction` (`item_id`, `action`, `quantity`, опционально `reasoning`), `AIBrainResponse` с `order_actions`, `is_recommendation`, `upsell_offered` / `upsell_offered_id` / `upsell_reasoning` и т.д. Дублировать схему в плане не нужно — источник правды один.

**Семантика:** пустой `order_actions` → полная замена корзины из `items`; при непустом `order_actions` и DRAFT — **merge** в `intent_router` / `merge_cart_actions`.

#### 4.4. Интеллектуальное управление корзиной

- [x] **State sync в промпте:** блок «Текущий черновик заказа» при активном DRAFT (`format_draft_order_context_for_prompt`).
- [x] **Incremental updates:** merge `order_actions` + `merge_cart_actions` в `intent_router` при существующем DRAFT.
- [x] **Re-calculation:** после merge — тот же пайплайн `validate_order` / `finalize_order_draft` / `compute_fee_lines` (пересчёт контейнеров, доставки и т.д.).
- [x] **Validation:** в промпте и ответе модели — не `remove` несуществующих строк; пустой merge → сообщение клиенту (см. `intent_router`).
- [ ] **Замена одного на другое:** в схеме нет отдельного `replace` — остаётся на качество модели и few-shot (можно расширить §4.6).
- [ ] **Natural language CRUD (полнота UX):** сложные фразы («убери всё кроме», «замени X на Y») — на стабильность модели; при необходимости — доп. эвристики или тесты §4.7.

#### 4.5. Блок «Активные продажи» (Upselling)

- [x] **Recommendation persona:** правила в `prompts.py` (тактика upsell, теги меню, `sales_strategy` с сервера).
- [x] **Триггеры (настраиваемые в БД):** таблица **`upsell_rules`** (§3.7 чек-лист) — триггер по категории/тегам корзины, `min_sum`, шаблон фразы; Strategy Engine (§4.12) применяет правила **после** LLM. Fallback — `sales_strategy` и промпт.

#### 4.6. Few-shot в промпте (стиль диалога)

В `prompts.py` уже есть **few-shot** для правок корзины и рекомендаций; при необходимости расширить **короткие примеры** в духе:

- **Клиент:** *«Что у вас вкусного?»*  
  **Бот:** *«Очень рекомендую плов „Праздничный“ — … К нему идеально лепешка из тандыра — …»* (конкретика по заведению подставляется из меню/KB, без выдуманных цен).
- **Клиент:** *«Давай, и убери из заказа колу, лучше чай.»*  
  **Бот:** *«Принято: заменил колу на чай. Плов и лепешку оставил в заказе. Проверим состав?»*

#### 4.7. Как тестировать

1. **«Забывчивость» / память корзины:** добавить 5 позиций по одной; попросить убрать **вторую** по счёту — бот должен корректно сопоставить с позицией в `items_json`, а не перепутать порядок.
2. **«Навязчивость»:** совет не должен повторяться без контекста; релевантность (к плову — салат/лепёшка, а не тот же десерт три раза подряд).

#### 4.12. Strategy Engine (Conversational Sales System) — дорожная карта

**Идея:** слой **после** ответа LLM и **до** отправки клиенту: детерминированные правила допродажи и анти-повторов дополняют промпт, не заменяя его.

**Целевой пайплайн:** `User → AI (AIBrainResponse) → Strategy Engine → (опц.) изменение reply_text / метаданных → intent_router → ответ`.

**Компоненты (к внедрению по модулям):**

1. **Context analyzer** — собрать `SalesContext` из текущего DRAFT (`items_json`), последней реплики, краткой истории, фрагмента меню: флаги вроде `has_drink`, `has_main`, сумма чека, множества отклонённых upsell, счётчик/время последнего предложения.
2. **Decision engine** — **без LLM**: правила («нет напитка» → `ADD_DRINK`, низкий чек → `LOW_CHECK_UPSELL`, `upsell_count > N` → `STOP` и т.д.). Пороги сумм и включение — из **`sales_strategy`** / БД (см. §4.5).
3. **Recommendation picker** — выбрать кандидата из меню по тегам/категориям, исключая уже в корзине и `rejected_upsell_iiko_ids`.
4. **Message enhancer** — одна ненавязчивая фраза с причиной («к плову обычно берут …»); не более **одной** рекомендации на сообщение.
5. **Trace** — продолжать вести **`order_meta.recommendation_trace`** (§4.8): offered / accepted, reason, `offered_iiko_id`.

**Анти-повтор:** уже частично в промпте и `rejected_upsell_iiko_ids`; цель Engine — **жёсткие** гарантии (не предлагать тот же SKU, cooldown в N сообщениях, хеш последних формулировок — опционально).

**Состояние в коде сейчас:** основная тактика в **`prompts.py`** + схема **`AIBrainResponse`** (`upsell_*`) + трасса и дашборд (§4.8). Strategy Engine — **выделение** этой логики из промпта в Python для тестируемости, A/B и единых правил между каналами.

**Связь с v3:** см. раздел **«### 8. Recommendation engine»** ниже — Strategy Engine является его конкретизацией для RestoMind.

## RestoMind v3 — Conversational Commerce Platform (blueprint)

Цель: зафиксировать **продакшен-уровень** для SaaS: деньги, нестабильность ИИ, масштабирование, отказоустойчивость, продукт. Это **не** обязательный объём следующего спринта — дорожная карта на несколько кварталов.

### 0. Главный принцип

**STATE → EVENTS → LOGIC → AI → UI**

- **STATE (БД)** — единственный источник истины по заказу и оплате.
- **EVENTS** — всё значимое фиксируется для аудита, аналитики, ретраев и интеграций.
- **LOGIC** — детерминированные правила (тарифы, валидация split, блокировки).
- **AI** — парсер намерений и генератор текста, **без** прямого управления деньгами.
- **UI** — отображение и действия оператора.

### 1. Слои и домены (явное разделение)

- **Слои:** API (FastAPI) → Application (`app/services`) → при росте — выделение **domain**-чистых модулей (pricing, payment) → Infrastructure (DB, Redis, внешние API).
- **Домены:** Conversation (state/history/intent), Order (items/pricing/packaging/delivery), Payment (split/validation/prepayment/**payment_events**), AI (parse/recommend), Admin.

### 2. Event-driven ядро (апгрейд)

События доменного уровня (лог + опционально очередь): `MessageReceived`, `AIResponseParsed`, `OrderUpdated`, `PaymentValidated`, `OrderConfirmed`, `OrderSentToIiko`. Минимум: **структурированные логи** + существующий **Redis pub/sub** для админки; максимум: запись в таблицу **`domain_events`** (audit).

### 3. Очереди вместо только `BackgroundTasks`

**Гибрид:** при `ARQ_ENABLED` и рабочем **Redis** вебхук WhatsApp ставит задачи в **ARQ** (`app/services/task_queue.py`, воркер `app/worker.py`: `whatsapp_process_text` / `voice` / `statuses`, `payment_notify_customer`); иначе — **BackgroundTasks** и тот же **`process_with_retry`** → **`failed_tasks`**. Цель v3: везде очередь, политики retry на уровне job, горизонтальное масштабирование воркеров без дублирования с API-процессом.

### 4. STATE: БД vs Redis

- **Истина:** `orders`; для диалога — **`users.current_state`**, **`current_pending_order_id`**, **`current_pending_booking_id`** (резерв Redis при eviction; восстановление в `dialog_mgr` при miss в Redis). Полноценная отдельная таблица **`conversation_state`** — опционально в v3 при росте нагрузки на аналитику state.
- **Redis:** кэш, быстрый state, история чата; при сбое — восстановление из полей `User` + `chat_logs` + DRAFT заказа.

### 5. Order Engine

- Ядро **`merge_cart_actions`** (есть) + **версионирование** (есть для обновления DRAFT) + в перспективе **idempotency key** на уровне действий (`action_id`).
- После каждого изменения: пересчёт total, packaging, delivery, валидация payment (уже в пайплайне).

### 6. Payment (уровень финтеха)

- Таблица **`payment_events`** — **есть** (админка + **`POST /api/webhooks/payment`**: `webhook_paid` / `webhook_failed`, идемпотентность по `note` = `provider_slug:payment_id`). На **`orders`**: колонки **`payment_provider`**, **`external_payment_id`** (заполняются при успешном webhook). **Цель v3:** журналировать **raw payload**, проверка **подписи/HMAC** провайдера, адаптеры под форматы эквайринга.
- **Инварианты:** нельзя подтвердить заказ при обязательной предоплате без `paid`/`waived`; при mixed — контроль расхождения split с итогом (в админке — валидация и блок подтверждения; полный пересчёт строк заказа — при появлении редактора состава).

### 7. AI: контроль

- Цепочка: **AI → JSON → Pydantic → validate → apply** (уже по сути).
- Разделение модулей: parser (intent/actions) / generator (`reply_text`) / recommender (upsell) — рефакторинг `ai_brain` по мере роста.

### 8. Recommendation engine и Strategy Engine

- **Сейчас:** reasoning и тактика в основном в промпте + **`recommendation_trace`** в `order_meta` (§4.8) + поля `upsell_*` в `AIBrainResponse`.
- **Цель:** гибрид **LLM (тон, формулировка)** + **Strategy Engine (§4.12)** — детерминированные триггеры, picker по меню, анти-повтор; отдельная таблица событий — при необходимости масштаба и A/B.

### 9. Observability

- Structured logs (JSON): intent, `order_actions`, результат merge, платежи; метрики latency (AI, STT, TTS), конверсия, upsell.

### 10. Fault tolerance

- AI: fallback `escalate` / шаблон (есть).
- Redis: деградация in-memory / восстановление из БД.
- iiko: retry + `iiko_last_error` + статус в админке (есть).

### 11. Voice

- Pipeline audio → STT → text → AI → TTS → audio; Phase 13.1 (streaming TTS, filler, метрики).

### 12. Security & multi-tenancy

- `organization_id` на сущностях (частично есть); rate limiting (есть); audit logs (события v3).

### 13. Feature flags

- Примеры: `ENABLE_UPSELL`, `ENABLE_VOICE`, `STRICT_AI_MODE` — безопасный rollout.

### 14. Roadmap v3 (порядок)

1. **Ядро:** versioning + idempotency входящих WhatsApp — **готово**; **merge `order_actions`** — **готово**; резерв state в **`users`** — **готово**.
2. **Очередь:** **ARQ** (Redis) — **опционально включена**; полный отказ от BackgroundTasks как fallback — **впереди**; при необходимости — расширенная таблица state.
3. **Расширение аудита оплаты:** **сырой payload** вебхука (и/или отдельная таблица событий) поверх текущих `payment_events` и колонок на заказе.
4. **Разделение AI-модулей.**
5. **Recommendation trace + аналитика.**
6. **Полноценный event bus + масштабирование воркеров.**

### 15. Чек-лист инфраструктуры и голоса (v3)

- [x] **Cloud Infra:** Upstash Redis через TCP `REDIS_URL` (`rediss://`), не REST-only.
- [x] **Consistency:** версионирование заказов (`orders.version` / `Order.row_version`, optimistic update в чате).

#### Как протестировать телефонию (пошагово)

Голос сложнее текста: помехи, акцент, **задержка (latency)** ответа.

**Шаг 1 — Голосовые сообщения в WhatsApp (бесплатно, уже в коде)**

1. Записать аудио на **разных языках**, например: «Маған екі палау және үш манты керек» (и отдельно узбекский / русский).
2. В логах бэкенда проверить: скачался ли файл; поле `recognized_speech` (если заполняется); корректны ли `intent` и позиции заказа (в т.ч. **плов 1кг + табак/казан**).
3. При `WHATSAPP_VOICE_REPLIES=true`: пришло ли **ответное аудио**; качество **Edge-TTS**.
4. Автотесты: `tests/test_ai_brain.py` (аудио), `tests/test_tts_edge.py`.

**Рекомендация:** начать приёмочные проверки с **қазақша и o‘zbek** в голосе; если заказ с контейнером «табак» стабильно проходит — ядро диалога + тарификация согласованы.

**Шаг 2 — Реальные звонки Twilio (SIP/PSTN), бюджет порядка $5–10**

1. **Публичный URL к dev:** например `ngrok http 8000` (или аналог), чтобы Twilio достучался до FastAPI.
2. **Twilio Console:** номер (~$1–2), Voice webhook / Media Stream → ваш WSS/HTTPS URL.
3. **Симулятор потока:** Python-клиент (`websockets`) с прогоном заранее записанного `.wav` в сокет и прослушиванием ответа — после появления реального `/voice/stream` в приложении.

**Шаг 3 — «Живой» стресс-тест**

- Попросить **не разработчика** наговорить или позвонить: быстрая речь, шум кухни/посуды.
- **Критерий:** устойчивое распознавание + **время от конца фразы до начала ответа**; если стабильно **> 3–4 с**, для PSTN высокий риск сброса — см. **Фаза 13.1**.

### Фаза 13 — Twilio Voice MVP

- Входящий PSTN → **Twilio Console** «A CALL COMES IN» = `POST https://<PUBLIC_BASE_URL>/api/whatsapp/voice/incoming` → TwiML (`Say` + `<Connect><Stream url="wss://…/api/whatsapp/voice/stream"/>`).
- WebSocket принимает **Media Streams** (μ-law 8 kHz), накапливает буфер (`TWILIO_VOICE_BUFFER_BYTES`, по умолчанию ~3 с), конвертирует в **WAV** (`audioop-lts`), **STT** через `openai_transcribe_voice`, далее тот же **`process_message`**, что WhatsApp.
- Ответ абоненту: **TwiML `Say` (Polly ru-RU)** через REST `Calls.update` — при активном одностороннем stream возможны ограничения Twilio; для «идеального» PSTN см. bidirectional stream / Фаза 13.1.
- Секреты: `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN` (подпись вебхука, если токен задан). Заготовка абстракций: `app/integrations/telephony.py`.

### Фаза 13.1 — Оптимизация latency (задержки)

Цель: удержать абонента на линии при ожидании модели.

- [ ] **TTS streaming:** начинать воспроизведение первых фонем/слоёв, пока модель ещё дописывает хвост ответа (архитектура зависит от выбранного TTS и транспорта Twilio).
- [ ] **Filler-фразы:** при ожидании OpenAI **> ~2 с** — короткий аудио/текстовый сигнал («Минутку…», «Считаю сумму…») до основного ответа (аккуратно с дублированием в WhatsApp-тексте).
- [ ] **Метрики:** логировать длительность этапов STT → LLM → TTS для SLA.

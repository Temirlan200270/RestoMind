# Чек-лист архитектурного аудита админки (UI/WS/AI)

Документ для регулярного “health check” админки RestoMind после крупных изменений UI/WS/AI.

Фокус: **Jinja + Alpine + один большой экран** (`app/templates/admin.html`) + realtime через WebSocket + latency цепочки ИИ.

Цель: быстро находить архитектурные проблемы **до** того, как они превратятся в “Perf 29 на всём”.

---

## Как пользоваться (коротко)

1) Открой админку на **mobile** и **desktop** (Chrome).  
2) Прогони **Lighthouse mobile** (`npm run lh:admin`) и сравни с прошлым `docs/ui/lighthouse/summary.json`.  
3) В DevTools сделай:
   - Performance trace 10–15 сек (mobile throttling),
   - снимок DOM (примерное количество узлов),
   - Network: старт после логина + переключение 2–3 вкладок,
   - при необходимости — WS reconnect (выключить/включить сеть на 2–3 сек).
4) Отметь пункты ниже: **OK / Риск / Проблема** и добавь ссылки на артефакты (Lighthouse reports, скрины, тайминги).

## 1) UI-архитектура (mobile + desktop): где “системно течёт” производительность

### 1.1. Один большой DOM + `x-show` (скрыто ≠ дешево)

- **Где смотреть**:  
  - `app/templates/admin.html` (вкладки/блоки)  
  - `app/static/js/admin-app.js` (состояния массивов, которые кормят `x-for`)
- **Почему это проблема**: даже если вкладка скрыта, большие списки (`orders`, `menuItems`, `chatList`) остаются в DOM/реактивности и “платят налог”.
- **Как измерять**:
  - **Chrome DevTools Performance**: запись 10–15 сек на mobile-профиле. Ищи “Recalculate Style / Layout” spikes при `loadOrders()`/WS событиях.
  - **Elements**: количество DOM-узлов после логина (mobile) и после `loadOrders()` — если растёт до тысяч, это ключевая причина Perf падения.
  - **Lighthouse**: плохой Perf на *всех* страницах — индикатор, что “общая страница тяжёлая”, а не только один экран.
- **Критерий OK**:
  - тяжёлые DOM-блоки не материализуются, пока вкладка не активна (ленивый DOM);
  - переключение вкладок не вызывает больших layout spikes при неизменных данных.

### 1.2. “Общий initial load” вместо “минимум + догрузки”

- **Где**: `app/static/js/admin-app.js` → `init()`, `loadTabData()`, логика `ws_ready`.
- **Почему**: всё грузится ради бейджей/комбайна сценариев; на мобильном это особенно больно.
- **Как измерять**:
  - **Network**: сколько запросов уходит сразу после логина и на переключении вкладок.
  - **Long tasks**: в Performance trace ищи long task > 50ms в первые 3–5 секунд после входа.
- **Критерий OK**:
  - после логина грузится минимум, достаточный для первого экрана;
  - тяжёлые загрузки — только по требованию (навигация/видимость).

### 1.3. Таймеры “на всякий случай” (resize/update графиков)

- **Где**: `admin-app.js` (цепочки `setTimeout(100/150/400/800…)`, принудительные `resize()/update()`).
- **Почему**: лечит гонки, но создаёт постоянную работу на слабом CPU.
- **Как измерять**:
  - **Performance**: даже “в покое” идут периодические JS tasks.
  - **Lighthouse Perf**: низкие Performance + высокий TBT/плохой INP (внутри отчёта).
- **Критерий OK**:
  - графики инициализируются/resize только когда реально видимы;
  - нет каскада таймеров при каждом переключении вкладки.

### 1.4. Смешение owner и operator UX в одном runtime

- **Где**: `admin.html`/`admin-app.js` (дашборд + операционные вкладки в одной странице/состоянии).
- **Почему**: owner-first dashboard и operator-first realtime имеют разные требования к данным/DOM.
- **Как измерять**:
  - если на owner-only сценарии (dashboard) Perf такой же плохой, как на orders — dashboard платит налог operator-части.
- **Критерий OK**:
  - owner-экран не тянет “операторские” данные/DOM, пока они не нужны.

## 2) WebSocket и realtime: что хорошо и где риски

### 2.1. Хорошее (уже сделано правильно)

- **Server**: `app/api/admin/ws.py` — токен, `ws_ready`.
- **Tenant scope**: фильтрация событий по `organization_id`.
- **Client**: один сокет, reconnect backoff, индикатор канала.

### 2.2. Риск: “дропаем события без `organization_id` молча”

- **Где**: `app/api/admin/ws.py` `_ws_event_allowed_for_org`.
- **Почему**: любой новый event без org просто не доедет → “UI иногда не обновился” без очевидной причины.
- **Как измерять**:
  - в логах сервера включить debug по “drop reason” (или временно добавить).
  - симптом: часть realtime работает, часть нет, но REST reload всё “чинит”.
- **Критерий OK**:
  - контракт событий явно требует `organization_id` и это проверяется/диагностируется;
  - drop событий виден в логах.

### 2.3. Риск: `ws_ready` триггерит тяжёлые REST перезагрузки

- **Где**: `admin-app.js` обработчик `ws_ready` (догрузка orders/stats).
- **Почему**: мобильная сеть → реконнекты → повторные `loadOrders()` → DOM раздувается, CPU горит.
- **Как измерять**:
  - **Network**: реконнект WS → сразу полетели крупные REST.
  - **Performance**: реконнект совпадает со style/layout spikes.
- **Критерий OK**:
  - после reconnect делается минимум восстановления (точечные данные), без full reload тяжёлых списков.

### 2.4. Риск: нет “seq/offset” → восстановление только через full reload

- **Где**: контракт событий (`app/services/events.py` и payload-ы).
- **Почему**: чтобы быть корректными, вы вынуждены “догружать всё”.
- **Как измерять**:
  - частота REST догрузок после WS событий/после reconnect.
  - “мигания” UI (WS показал, REST потом изменил обратно).
- **Критерий OK**:
  - есть дешёвый способ восстановиться (версия/seq/минимальные патчи или ограниченный refresh).

## 3) Событийная шина (publish/subscribe): скрытые архитектурные долги

### 3.1. Смешивание realtime и внешних уведомлений в одном awaited пути

- **Где**: `app/services/events.py` → `publish_event()` → `await notify_staff_from_event(...)`.
- **Почему**: Telegram/внешние API могут замедлять путь публикации; в пике это увеличит tail latency.
- **Как измерять**:
  - тайминг логов/pipeline stages (publish start → publish done).
  - сетевые ошибки Telegram коррелируют с лагом UI/вебхука.
- **Критерий OK**:
  - WS publish не ждёт внешние уведомления; уведомления — асинхронно/очередью.

### 3.2. In-memory fallback очереди: “тихий сброс” при нагрузке

- **Где**: `events.py` `_broadcast_in_memory`, `QueueFull → subscriber discard`.
- **Почему**: при всплеске событий WS-клиенты могут терять подписку (и вы лечите это full reload-ом).
- **Как измерять**:
  - метрика/лог “QueueFull” + корреляция с последующими REST перезагрузками/падением ws-ready статуса.
- **Критерий OK**:
  - при overflow есть наблюдаемость и контролируемая деградация (а не “тихий отвал”).

## 4) Латентность ИИ: где архитектурно может быть хуже, чем должна

### 4.1. Хорошее: WhatsApp pipeline уже разделяет “DB read → LLM → DB write”

- **Где**:
  - `app/api/webhooks.py` (LLM вызывается вне DB-сессии)
  - `app/services/context_engine.py` (параллельный сбор контекста)
- **Эффект**: снижает риск “DB pool starvation” и уменьшает хвосты.
- **Критерий OK**:
  - DB-сессии короткие; LLM/STT/TTS не держат соединения.

### 4.2. Плохое: test-bot держит DB-сессию во время LLM

- **Где**: `app/api/admin/test_bot.py`.
- **Почему**: удержание соединения во время LLM = хуже latency всего админ-бэкенда при параллельных запросах.
- **Как измерять**:
  - при нескольких test-bot запросах растёт время ответа обычных admin REST.
  - появляются ожидания/деградация под нагрузкой.
- **Критерий OK**:
  - test-bot следует той же фазной схеме, что и WhatsApp: read → LLM → write.

### 4.3. Контекст “дороже, чем нужно”

- **Где**: формирование menu/kb/draft/customer контекстов (`order_logic`, `knowledge_context`, `customer_context`).
- **Почему**: каждый токен = latency + cost; особенно если меню большое.
- **Как измерять**:
  - размер контекста (символы/токены) и корреляция с временем LLM.
  - сравнение demo (малые данные) vs реальный каталог.
- **Критерий OK**:
  - контекст ограничен/сжат/кеширован на org-уровне; нет полного меню в каждом запросе без необходимости.

### 4.4. Retry политика: может ухудшать UX хвостами

- **Где**: `process_with_retry()` MAX_RETRIES=3 + backoff.
- **Почему**: пользователь ждёт долго, хотя иногда лучше раннее degrade/escalate.
- **Как измерять**:
  - счётчик retries + распределение времени ответа (p95/p99).
- **Критерий OK**:
  - ретраи не раздувают хвосты; для transient LLM ошибок есть быстрый degrade/escalate.

---

## 5) WS “настроены хорошо?” — итог без кода

- **Да, базовые принципы хорошие**: токен, org-scope, reconnect, `ws_ready`.
- **Но архитектурно** WS сейчас вынуждает UI делать тяжёлые REST reload-ы, потому что **нет дешёвого способа восстановиться** (seq/offset/минимальные патчи) и потому что UI тяжёлый сам по себе (DOM).

## 6) Дальнейшие шаги (без реализации): приоритизация

### P0 (самый большой эффект)

- Сделать вкладки действительно ленивыми по DOM, а не только по данным (особенно orders/chats/settings blocks).
- Убрать LLM внутри DB-сессии в `test_bot` (привести к WhatsApp архитектуре).
- Развязать `publish_event` и внешние уведомления (realtime не должен ждать Telegram).

### P1 (стабилизация perf и WS)

- Уменьшить “full reload” на WS reconnect: минимум данных вместо `loadOrders()` всегда.
- Свести графики к “инициализация только при видимости” без множества таймеров.
- Кеш/сжатие AI-контекста (меню/KB) на org-уровне.

### P2 (платформенный уровень)

- Контракт событий: обязательные поля, версия, поведение при drop; диагностика пропусков.
- Разделение сценариев owner/operator по данным и UI-структуре.
